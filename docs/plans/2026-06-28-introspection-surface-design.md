# Design: cc-clip Introspection Surface (status / doctor) — precursor to any settings UI

Generated by /office-hours on 2026-06-28
Branch: main
Repo: ShunmeiCho/cc-clip
Status: DRAFT
Mode: Builder

## Problem Statement
The original ask was "build a UI to configure cc-clip's local settings, and what should it
include?" Reframed during office hours: the real pain is **not** changing settings, it is
**seeing state**. cc-clip's true runtime state is scattered across the local daemon, the token
file, launchd, the remote shim, remote deploy state, notify config, and the SSH tunnel. When
something breaks, the user's first need is "what is the state right now?", not "what do I
change?". The missing primitive is a **canonical introspection surface**. A config UI built
before that just wraps unknown state in a nicer box.

## What Makes This Right (not just cool)
A single typed model of "current cc-clip reality" that every later surface reads from. Get this
right and `status`, a future `config` subcommand, and an eventual TUI/GUI all compose without
re-implementing data gathering. Get it wrong (gather data inside each command) and every new
surface re-derives state and drifts.

## Sequencing (user's call, endorsed)
1. CLI introspection: `cc-clip status` / `--host <h>` / `--json` FIRST.
2. `cc-clip config` mutation subcommand SECOND (reads the same model).
3. TUI/GUI LAST, only once the read model is canonical.
Do NOT build a GUI first.

## Premises
1. Introspection precedes configuration UI — agree.
2. The model must tag every field with `source: file | live | env | default` and a timestamp
   (FILE written-at vs LIVE probed-at). A present token file != a daemon running with it.
3. Security invariant: never print token / nonce / session values. Report presence + age /
   expiry only; partially mask any identifier shown.
4. Local status must be fast and SSH-free. `--host` (remote probe) is opt-in and slow (seconds).
5. `--json` is the lever that forces a single data model; it must back every future surface.
6. `--json` exits non-zero when unhealthy so it is usable in scripts / CI / hooks.

## Approaches Considered
### Approach A: Thin status command (minimal viable)
`cmdStatus` calls existing subsystem accessors and prints a report + `--json`.
Effort S, Risk Med. Fastest. Con: data gathering lives in the command, so a later TUI/config
re-implements it — the "wrap unknowns" trap, deferred.

### Approach B: Canonical Inspector model (ideal) — RECOMMENDED foundation
New `internal/inspect` package produces a single typed `Snapshot` (local + optional remote),
each field `{value, source, takenAt}`. `cmd/cc-clip status` is one renderer (text/json) over
`Snapshot`. Future `config` and any TUI/GUI read the same `Snapshot` plus a parallel typed
mutation API. Effort M, Risk Low. Best trajectory; makes the status->config->TUI sequence
compose without rework.

### Approach C: doctor-first lens (lateral)
Default output is a derived health verdict ("3 things need attention: token expired; venus shim
off PATH; Codex host but Xvfb down"), raw fields behind `--verbose`. Same underlying model as B.
Optimizes for the real moment: "something's wrong, what is it?"

## Recommended Approach
**B as the foundation (typed `Snapshot` + `internal/inspect`), with C's health verdict as the
default rendering.** Raw fields under `--verbose`; full data under `--json`. This realizes the
canonical introspection surface and avoids unknowns-in-a-box because every later surface reads
one model.

## What the surface should include
### Local (no SSH, fast)
- Binary: path, version, install method.
- Daemon: running? (LIVE loopback probe), port, PID, uptime.
- Token: file present? (FILE), expiry/age (FILE), accepted by running daemon? (LIVE authed probe).
  Never the value.
- Service (launchd): installed / loaded / running (LIVE via launchctl), plist path.
- Notifications: sound, icon, enabled, urgency tiers — resolved value + source per field.
- Config sources: which `CC_CLIP_*` env vars are set, config file path + presence, max image
  size, resolved out-dir.
- Host registry: hosts + per-host Codex flag (FILE).

### Per-host (`--host`, SSH, opt-in, slow)
- SSH reachability (master).
- Remote binary version / path.
- Shim installed? (xclip/wl-paste) and does PATH resolve to the shim?
- Remote token / session present (presence, not value).
- Codex: Xvfb running? x11-bridge running? DISPLAY marker present?
- Claude hooks: managed hooks in settings.json? legacy wrapper present?
- Notify: nonce present? health log last status?
- opencode / antigravity flags.
- Tunnel: end-to-end reachability from remote back to local daemon (the real connectivity check).

### Value-add gaps (not in the original list)
- Derived **health verdict** (the status-vs-doctor difference) — highest value.
- **provenance as a first-class field** on every value.
- **`--json` exit-code semantics** for scripting/CI/hooks.
- **Redaction + timestamps**: mask identifiers; show FILE-written-at and LIVE-probed-at.

## Premise / Risk notes
- `--host` latency: keep remote probes parallel where safe and clearly marked LIVE; default to
  local-only.
- Probes must be read-only and never mutate remote/local state (introspection != deploy).
- Reuse existing accessors (token.ReadTokenFileWithExpiry, daemon Probe, service.Status,
  hosts.Registry, shim deploy state, xvfb/x11bridge PID files) rather than re-deriving.

## Open Questions
- Does `--host` reuse the ControlMaster SSH session, or open a short-lived one? (latency vs setup)
- Should `doctor` propose fixes (actionable) or only diagnose? (likely diagnose + suggested command)
- Where does `config` write land (env / config file / plist) given today's scattered sources —
  needs its own office-hours once status exists.

## Success Criteria
- `cc-clip status` answers "what is the state right now?" locally in < 300ms, no SSH.
- `cc-clip status --json` is a stable, documented schema that a TUI/GUI/config could consume
  unchanged.
- Health verdict surfaces the common failure modes (expired token, shim off PATH, Codex host
  with Xvfb down, tunnel unreachable) without the user reading raw fields.
- No secret value is ever printed.

## Distribution Plan
Ships in the existing cc-clip binary via goreleaser tag releases — no new distribution channel.

2. Build local-only `internal/inspect` + `cc-clip status` (text + `--json`), reusing existing

## Snapshot Schema Draft v2 (revised after code-grounded review)

Status: contract-calibration. Do NOT generate `internal/inspect/snapshot.go` yet — land and
stabilize the schema here first. All 7 review findings below were verified against the code.

Changes from v1:
1. `Source` gains `flag` — `getPort()` (cmd/cc-clip/main.go:198-208) is default→env→flag; `--port`
   overrides `CC_CLIP_PORT`, so env/default alone misrepresent provenance.
2. `Field[T]` gains `Known bool` + `Error string` — a `bool false` / `int 0` must be
   distinguishable from "not determined". Invariant: when `Known=false`, `Source` is `unknown`
   or `Error` explains the probe failure.
3. `RegistryInfo.Hosts` becomes `[]RegisteredHost` mirroring `hosts.Entry`
   (registry.go:43-47): `LastConnected`, `LastDeployedVersion`, `Codex` — not just host names.
4. Human strings out of the machine contract: `Daemon.Uptime`→`StartedAt *time.Time`,
   `Secret.Age`→`ModifiedAt *time.Time`. Text renderers format; consumers get raw time.
5. Secret modeling split: `AuthTokenInfo` (has expiry + live `Accepted`) for the session token
   (token.go has expiry) vs `SecretFileRef` (presence + path + modifiedAt only) for the remote
   session file and notify nonce, which have no expiry/acceptance semantics.
6. `ServiceInfo` reflects platform reality: `service.Status()` (launchd.go:151-153) returns one
   merged loaded/running bool. Model `Manager` (`launchd`|`windows-run-key`) + `Configured`
   (FILE: plist/Run-key present) + `Running` (LIVE merged). Drop the fake cross-platform `Loaded`.
7. `NotifyInfo.Adapters` mirrors `shim.AdapterState` (deploy.go:40-46) keyed by adapter
   (`claude-notify`/`codex-notify`/`opencode-notify`/`agy-notify`) so a renderer can show WHICH
   adapter failed — `NoncePresent`/`LastHealth` alone hid that.

```go
const SchemaVersion = 1

type Source string
const (
	SourceLive    Source = "live"
	SourceFile    Source = "file"
	SourceEnv     Source = "env"
	SourceFlag    Source = "flag"
	SourceDefault Source = "default"
	SourceUnknown Source = "unknown"
)

// Field. Invariant: Known=false => Source==SourceUnknown OR Error is set.
type Field[T any] struct {
	Value   T         `json:"value"`
	Source  Source    `json:"source"`
	TakenAt time.Time `json:"takenAt"`
	Known   bool      `json:"known"`
	Error   string    `json:"error,omitempty"`
}

// AuthTokenInfo: the session token (has expiry + live acceptance). Never the value.
type AuthTokenInfo struct {
	Present   Field[bool]       `json:"present"`
	Path      Field[string]     `json:"path"`
	ExpiresAt Field[time.Time] `json:"expiresAt"`
	Accepted  Field[bool]       `json:"accepted"`           // LIVE; Known=false if daemon down/unchecked
}

// SecretFileRef: a secret file we confirm exists + when it changed. Never the value.
// Used for the remote session file and the notify nonce.
type SecretFileRef struct {
	Present    Field[bool]       `json:"present"`
	Path       Field[string]     `json:"path"`
	ModifiedAt Field[time.Time] `json:"modifiedAt"`
}

type DaemonInfo struct {
	Running   Field[bool]       `json:"running"`
	Port      Field[int]        `json:"port"`
	PID       Field[int]        `json:"pid"`
	StartedAt Field[time.Time] `json:"startedAt"` // consumer derives uptime
}

type ServiceInfo struct {
	Manager    Field[string] `json:"manager"`    // "launchd" | "windows-run-key"
	Configured Field[bool]   `json:"configured"` // FILE: plist / Run key present
	Running    Field[bool]   `json:"running"`    // LIVE: merged loaded/running
	PlistPath  Field[string] `json:"plistPath,omitempty"`
}

type RegisteredHost struct {
	Host                string     `json:"host"`
	LastConnected       *time.Time `json:"lastConnected,omitempty"`
	LastDeployedVersion string     `json:"lastDeployedVersion,omitempty"`
	Codex               bool       `json:"codex"`
}

type RegistryInfo struct {
	Path  Field[string]           `json:"path"`
	Hosts Field[[]RegisteredHost] `json:"hosts"`
}

// AdapterStatus mirrors shim.AdapterState.
type AdapterStatus struct {
	Installed bool   `json:"installed"`
	Source    string `json:"source,omitempty"`
	Version   string `json:"version,omitempty"`
	Verified  bool   `json:"verified"`
	LastError string `json:"lastError,omitempty"`
}

type NotifyInfo struct {
	NonceFile SecretFileRef                   `json:"nonceFile"` // presence only
	Adapters  Field[map[string]AdapterStatus] `json:"adapters"`  // keyed by adapter id
}
```

Unchanged from v1: `Snapshot`/`Health`/`Problem`/`Severity`, `BinaryInfo`, `NotificationInfo`,
`ConfigInfo`, and the per-host structs (`HostState`, `RemoteBinary`, `ShimInfo`, `CodexInfo`,
`ClaudeHooksInfo`, `RemoteFlags`, `TunnelInfo`) — except local token uses `AuthTokenInfo`, and
remote session/nonce use `SecretFileRef`.

### Resolved invariants (schema FROZEN)
These two base-contract decisions are frozen; do not revisit when generating Go.
1. **`TakenAt` is per-field and means "when this field was observed/parsed/decided"** — distinct
   from the top-level `GeneratedAt` (envelope assembly time) and from any underlying timestamp
   (file mtime, token expiry, daemon start). It is set even when `Known=false` (the "when we
   tried" time), which is what slow `--host`, concurrent probes, partial failure, and staleness
   checks need.
2. **`Known` is the single unknown signal.** No pointers, no `omitempty` on value-bearing fields:
   time fields are `Field[time.Time]`, `Accepted` is `Field[bool]`. When `Known=false`, `value`
   is the zero value and consumers MUST ignore it. One null path, uniform field shape across the
   whole schema.

With these frozen, the next step is `/plan-eng-review` (probe concurrency, reader mapping, the
`--host` slow path), then generate `internal/inspect/snapshot.go` as zero-logic types.
